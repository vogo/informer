# 设计

本文记录 informer 的实现取舍与约束。产品是什么、有哪些功能、怎么使用，见 [README](../README.md)；命令行操作见 [cli-usage.md](../cli-usage.md)。

桌面版（`cmd/informer-ui`，Wails v3 + Vue 3 + Naive UI）与命令行（`cmd/informer`）共用同一个数据目录和 Service 层，可以同时运行。

## 系统运行日志

桌面版从 Finder 或开始菜单启动时，stdout 没有人看得到：凌晨定时推送失败，第二天没有任何痕迹可查。进程把自己写出的每一行日志同时留一份在内存里（默认最多 2000 行，stdout 照旧输出），窗口右上角的「日志」打开面板即可翻看。

- **内容**：定时任务的触发与结果、每次抓取的请求与解析、推送到机器人的结果、启动失败的原因。也就是订阅页「测试抓取」里那种执行日志，加上不属于任何一次测试抓取的后台运行记录。
- **筛选**：按级别（全部 / 警告与错误 / 仅错误）和关键字过滤。「复制」复制当前筛选结果，「清空」丢掉已有的行，只看接下来发生的事。
- **跟随**：面板打开时每秒读取一次新增行并滚到底部。向上滚动即暂停跟随，回到底部恢复。也可以关掉「自动刷新」，改用「刷新」按钮手动读。
- **边界**：日志只活在本次运行的内存里，不落盘，重启后清空。超过上限时最早的行被覆盖，面板写出「已省略较早的 N 条」，不把日志假装成连续的。启动失败时面板照常可用。

测试抓取抽屉底部的「执行日志」是同一种实时输出，范围限于这一次抓取：请求地址与 HTTP 状态码、正则 / JSON 路径的匹配情况、逐条解析出的标题与链接；agent 类型还会显示完整提示词、每一次搜索与网页抓取、以及返回的原文。抓取中面板自动展开（日志就是进度），成功后自动折叠，失败则保持展开。

## AI 辅助改配置

诊断修复和定义配置用的是「设置」里同一套 Agent（接口地址、密钥、模型）。同一时间只允许跑一个 AI 任务，两者共用一个闸。

Agent 没有写库的能力。它把结论或候选配置交回 informer，由 informer 自己再跑一遍解析复核；复核通过才出现可确认的按钮，确认之后才写库。

### 工具与隔离

informer 把自己的工具做成一个 MCP server，由 agent 命令行以 `--strict-mcp-config` 加载。这次会话除了这些工具和只读的 WebSearch / WebFetch 之外，碰不到别的东西，尤其够不到数据库。工具进程读的是一份临时快照文件，运行结束即删除。

探索和判定是分开的：

- **探索**可以用 WebSearch / WebFetch：找站点的 feed 地址、确认是不是改版、查接口文档。只盯着一份文档看，形成不了假设。
- **判定**必须落回 informer 自己的字节。结论以 informer 抓取工具取到的内容为准，候选配置都要真的试跑过。informer 抓取时带着该订阅的 curl 请求头和全局代理；换一种抓法拿到的字节不一样，据此做的「页面格式变了」就是错的。

试跑不写任何数据。

### 诊断修复

抓取失败（网页改版后正则或 JSON 路径不再匹配）时，订阅卡片上有「AI 诊断修复」。Agent 可以读订阅配置与失败原因、按 informer 自己的方式抓取页面原文、用候选配置真实试跑，并反复「改正则 → 试 → 再改」。

- informer 拿到建议后自己再复核一次。复核解析出文章才亮出「应用修复」。Agent 自称修好、复核没通过时，面板说明这件事，不提供一键应用。
- 抽屉逐字段列出「原值 → 新值」，以及复核解析出的前几条标题，用来确认那是文章而不是导航栏或广告。点「应用修复」才写库，并立刻重新抓取一次。修好了状态恢复正常；仍然失败则保留失败状态和新的错误信息。
- 能改的字段只有：订阅地址、自定义请求、解析类型及其参数（正则 / 表达式 / JSON 路径 / Agent 提示词）、链接重定向。标题、分类、权重、启用状态不在职责范围内。
- 站点关闭、需要登录、内容改由 JS 渲染时，面板给出结论和建议（换订阅地址、改用 agent 类型、或删除这个订阅），不硬凑一个能匹配到东西的正则。
- 诊断通常要一到几分钟。抽屉底部的「诊断日志」实时输出每一步：重试当前配置、agent 每一次工具调用、复核结果。

### 定义配置

新建订阅时，难的是判断该用哪种解析方式并把正则或 JSON 路径写对。「AI 定义配置」把这一步交给同一个 Agent：用大白话说清楚想订阅哪里的什么内容，由它来试。

解析方式按固定顺序选择，不凭感觉：

1. 先试标准 feed：把给出的地址原样试一遍，再去页面 `<head>` 里找 `<link rel="alternate">`，再依次探 `/feed`、`/rss`、`/atom.xml` 等常见路径。feed 是站点改版后唯一还能继续工作的形态，所以必须先排除。
2. 响应体是 JSON 就用 JSON 路径，不用正则。
3. HTML 列表页才写正则。
4. 只有压根没有可抓地址、或内容由 JS 渲染时，才退到 agent 类型。那意味着每次定时抓取都要真跑一次 AI，慢且贵。

工具和诊断是同一套：按 informer 自己的方式抓页面、用完整候选配置真实试跑，外加只读的 WebSearch / WebFetch 做探索。

「解析出东西」不算成功。标题必须是文章标题而不是导航栏、分页或广告；链接必须是每篇文章各自的地址。解析出好几条却都指向同一个地址，当场判为失败。

配置必须通过专门的工具交给 informer，在回复里用文字描述不算数。informer 再跑一遍解析，核对通过才在聊天里出现「保存并新建订阅」。提案逐字段列出解析类型、地址、正则或路径，以及复核解析出的前几条标题。旁边可以选分类（也可以直接输入新分类名）；标题用 AI 起的那个，可以改。

agent 类型的提案不做自动复核，因为那会在当前 agent 里再启动一个 agent。这种提案标注「未复核」，仍然允许保存；保存后要用订阅卡片上的「测试抓取」验证一次。

每一轮通常要一到几分钟，聊天下方的「执行日志」实时输出每一次抓取和试跑。一次对话最多 12 轮：每轮都会把整段对话重发一次，太长的对话不如重新开始。

## 订阅导入与导出

导出写的是**全部**订阅，不受左侧分类和过滤条件影响。每个订阅导出完整配置（标题、URL、curl、解析类型及其参数、Agent 提示词、抓取选项、启用状态），分类**按名字**导出。数据库自增 ID 和抓取状态（正常 / 失败及错误信息）不导出，它们只属于本机。

导入的认法：有 URL 的订阅按 URL，没有 URL 的（Agent 订阅本来就没有地址）按标题。能对上的覆盖其配置，本机的抓取状态保留；对不上的追加为新订阅。导入不会删除任何订阅，所以一份只含几条订阅的文件只会新增和更新这几条。

文件里的分类名本机没有时自动创建；分类名为空则归入「未分类」。某一条既没有 URL 也没有标题、或 Agent 订阅缺提示词时，跳过并在结果里逐条列出，其余照常导入。

文件版本比当前程序新时整体拒绝导入，以免把不认识的字段悄悄丢掉。手写文件也可以直接是一个 JSON 数组，不带外层对象。

## 历史索引重建

库里若有一批文章的通知时间（`informed_at`）是空的，「设置 → 重建历史索引」从已经生成的日报 Markdown 里补：

- **判定依据只有链接**。从日报里提取文章链接，与库中文章的 URL 做精确匹配。只有「恰好匹配到一条、且该文章的通知时间为空」才会补值。补的是该日报当天的本地 00:00（精度到天，因为文件名只能证明到天）。
- **不覆盖、不编造**。已经有通知时间的文章原样保留。库里找不到的链接、匹配到多条文章的链接，一律跳过并保持为空。
- **可重复执行**。第二次运行只会把第一次补好的记录报告为「已有时间」。

执行后给出扫描天数、链接数，以及成功 / 跳过（分「已有时间」「库中无此链接」「匹配到多条」）/ 失败的数量。

## 日报与文章库

- 日报 Markdown 以关闭原始 HTML 的方式渲染，并在注入 DOM 前做一次消毒。报告里的链接一律走系统浏览器打开，不会让 WebView 自身跳转。
- 日期只接受 `2006-01-02` 这一种写法，由后端校验。界面无法读到数据目录以外的文件。单日内容一次性加载，不分页。
- 文章库翻页用文章 ID 作游标而不是 offset。定时任务在翻页期间插入新文章也不会造成重复或漏项。切换筛选条件会回到第一页。

## 配置文件

`informer.json` 是一份人类可读的整份 JSON，不入库，不做版本历史，也不提供回滚。字段含义与取值见 [README 的配置一节](../README.md#配置)。

无论命令行手写还是桌面版「设置」页保存，写入都遵守：

- **保留未知字段**。保存只替换 `feed`、`agent`、`result_processing`、`schedule`、`webhooks` 与 `http_proxy`。文件里其它顶层字段（包括这个版本还不认识的字段）连同顺序一起原样保留。
- **原子替换**。先写同目录下的临时文件再 `rename` 覆盖。并发运行的 crontab 读到的要么是旧文件、要么是新文件，不会读到写了一半的内容。
- **跨进程写锁**。写入前创建 `informer.json.lock`，两个「读—改—写」不会互相覆盖造成丢失更新。锁有等待上限，等不到会直接报错而不是一直卡住。进程被杀留下的陈旧锁会在明显过期后被自动接管。
- **拒绝即不改文件**。`same_site_max_count`、`feed_expire_days`、`max_inform_feed_size` 为 0 会让推荐算法选不出任何文章，因此被拒绝；超出合理范围的值同样被拒绝。被拒绝的保存不会改动文件。

`INFORMER_HOME` 指向的目录无法创建或不可写时，informer 直接报错退出，不退回到另一份数据继续跑。informer 不会自动同步多个数据主目录，也不支持同时使用多个 `INFORMER_HOME`。

### 敏感配置

Agent API Key 放在数据主目录的 `informer.secret.json` 的 `agent_api_key` 字段，不写进 `informer.json`。该文件无论新建还是改写，权限都会被设置并校验为 **0600**；权限无法落实时保存直接失败，不以不安全的状态写下去（Windows 不支持 Unix 权限位，这一步在 Windows 上无法校验）。桌面版「设置」页只显示「是否已配置」，不回传原文。

`base_url` 与 `agent_api_key` 都留空时，informer 直接运行本机 Agent，用的就是该 Agent 自身已登录的凭据。

### 多目标推送

机器人目标写在 `informer.json` 顶层的 `webhooks` 数组，不进入 secret 文件。每项是
`{"name": "", "url": "", "enabled": true}`：`url` 必填，`name` 可选（缺省显示域名），
`enabled` 缺省为 `true`；地址为空或重复的保存会被拒绝。

- **全量广播**。每次运行把同一份消息**并发**投递给所有启用的目标，不做订阅与目标之间的绑定。
  并发是为了让多个卡住的目标共享同一段客户端超时，而不是逐个叠加等待。
- **部分失败不算失败**。逐目标记录结果；只要至少一个目标接受，运行就算成功，文章照常写入
  `informed_at`，界面列出失败的目标名与原因；只有全部目标失败才返回错误、不写通知时间。
- **没有逐目标补推**。`informed_at` 是文章级字段，不是「文章 × 目标」的记录，失败的目标不会被
  单独补推。需要补发时只能等下一次运行，或手动推送整份日报。
- **兼容旧配置**。旧版本的单个 `webhook` 字段（在 `informer.json` 或 `informer.secret.json`）
  仍会被读取；下一次保存把地址写入 `webhooks` 并在同一次写入中删掉旧键，同时清理 secret 文件里
  的旧字段。命令行参数传入的地址替换本次运行的目标列表，只推这一个。

### Agent 可执行文件

桌面版从 Dock / Finder 启动时往往没有终端里的 PATH。`agent.command` 留空时，informer 会在 PATH、Homebrew / npm / nvm 等常见目录以及登录 Shell 里查找 `claude` / `codex`，并把绝对路径写回 `informer.json`。设置页也可以手动填写或点「自动查找」。`codex` 已预留，本版本运行时会报错。

`http_proxy` 供 URL 抓取、桌面版应用内更新与 Agent 子进程共用。有配置时，订阅抓取、每日鸡汤、机器人推送与检查 / 下载新版本走共享 HTTP 客户端；Agent 子进程会注入 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY`。这与 `agent.base_url`（API 网关地址）无关。

## 定时推送

`schedule` 只被桌面版读取。命令行与系统 crontab 忽略它，命令行的定时推送仍由 crontab 负责。

桌面版定时仅在应用保持打开时生效。每个自然日最多成功推送一次，记录在数据目录的 `informer.schedule-state`：重启同一天不会再补推；失败会在下次轮询重试。当天过了设定时间才打开应用，会补推一次。

## 应用内更新

正式发布构建在启动时及之后每 24 小时检查一次 GitHub Releases。若有新版本则后台下载并校验，右上角出现「重启生效新版本」，点击后替换二进制并重启。开发版（`version=dev`）不发起检查。

macOS 安装包未做代码签名与公证。首次打开以及自更新替换后，可能需在「系统设置 → 隐私与安全性」中放行。

打 `v*` 标签后，由 `.github/workflows/release.yml` 在 macOS / Windows / Linux 三个原生 runner 上构建桌面版与命令行版，并聚合发布到 GitHub Release（桌面安装包、应用内更新用的 zip / tar.gz、命令行 `informer-cli` 压缩包，以及固定名 `SHA256SUMS`）。当前阶段不做代码签名 / 公证。

## 当前不做

不做拖拽排序，不做全文搜索。配置不迁移到数据库，不提供配置的版本历史或回滚，也不支持多用户 / 多环境配置。

## AI 最终结果处理

`result_processing` 是可选顶层配置，只有 `enabled` 和 `prompt`。缺省关闭；开启时提示词必填。CLI、桌面手动与定时均通过 `service.TriggerInform → inform.Run` 使用同一条处理链。

- **顺序**：抓取入库 → 规则选候选 → 原始日报 → 可选 AI 处理 → 校验 → 原子保存正式日报 → 并发推送 → 记录最终选中文章的 `informed` 与 `informed_at`。选择候选不再提前修改 `informed`，被过滤或发送失败的文章仍可重试。
- **输入**：日期、原始日报、候选文章 ID、标题、URL、来源 ID、来源域名和发布时间。第一版没有正文；不自动补选，也不联网补充信息。
- **执行**：复用 Agent 的命令、模型、凭据、代理与超时，显式以 `--tools ""` 关闭工具。桌面预览、推送、诊断和配置对话共用 Agent 运行互斥锁，避免 AI 任务重叠。
- **输出契约**：`action`（`publish` / `skip`）、`summary`、保留的 `articles[{id,reason}]` 与过滤的 `rejected[{id,reason}]`。每个候选 ID 必须恰好出现一次；未知、重复、遗漏 ID、空原因、空导读及不一致的 action 均拒绝。允许 JSON 代码围栏，不接受说明文字。模型提供的 `content` / `raw` 字段不被采用。
- **渲染**：程序根据真实记录生成日期、中文导读、精选文章的标题、链接和推荐原因。模型的导读和原因不接受 URL 或 Markdown 链接，防止编造链接进入推送及历史索引。
- **无结果与失败**：`skip` 是成功完成，不保存新日报、不推送、不标记文章，桌面定时正常消费当天。调用或校验失败则停止，不回退原始内容，不覆盖当天已有日报。保存日报失败同样停止推送。多目标推送的部分成功规则保持原样。
- **运行记录**：调用前就将候选、原始日报和提示词写入 `runs/<日期>/processing-*.json`，处理后追加模型原文、筛选结果或错误；文件为 0600。记录不在 `data/` 下，不参与日报浏览和历史索引重建。它是处理阶段记录，不是机器人送达凭证。
- **预览**：读取文章库现有未通知候选和已保存的 Agent 设置，使用当前未保存的提示词调用同一处理器；不抓取，不写日报、运行记录或配置，不更新数据库，不推送。预览时不执行会自动持久化命令路径的发现逻辑。

被过滤的文章第一版不作永久排除，可能在后续日期重新参与模型筛选，直到现有候选规则不再选中它们。
